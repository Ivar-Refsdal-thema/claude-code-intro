Claude Code — Hands-on tasks

Now that you've seen the four demos, pick a task below and work through it with Claude Code.

Getting started

Six tasks, roughly in order of "warm-up" to "open-ended." You don't need to finish all of them — pick what looks interesting and go as deep as time allows.

Folder structure

Each task has a matching empty folder under tasks/ — build your solution there so it's obvious what belongs to which task:

tasks/task-1-github-mcp/
tasks/task-2-skills-agents/
tasks/task-3-price-notebook/
tasks/task-4-elhub-dashboard/
tasks/task-5-hydrology-dashboard/
tasks/task-6-freeform/

Use your own branch

Before starting a task, branch off — but a plain name like task-1-github-mcp will collide the moment two people in the room use it against the same remote. Work something unique to you into it, e.g.:

git checkout -b <your-name>/task-1-github-mcp

Commit as you go — ask Claude to do it, or use /commit if you built the skill in Demo 4.

Tip: once Task 1 has GitHub MCP connected, ask Claude to create the branch for you on the tasks after that — it can check what already exists on the remote and avoid a collision itself.

Environment

If a task needs a Python environment, just ask Claude to set one up — uv is a good default (Claude can install it for you if it's missing). For a quick Streamlit check without uv, pip install streamlit works fine too.

Still applies

Shift+Tab to cycle modes · Esc / Esc Esc to interrupt or rewind · /clear for a fresh task · /context to see what's filling the window · ! to run a shell command without leaving Claude Code.

Task 1 — GitHub MCP

tasks/task-1-github-mcp/
Goal: connect Claude Code to GitHub and use it to interact with this repository.

1. Set it up

Follow the official guide: github.com/github/github-mcp-server. If you already have a github MCP server configured from Demo 4, you're done — check with:

claude mcp list

2. Try it out

Figuring out what to ask for is the task — no scripts here. A few directions worth exploring on your own: confirming who you're authenticated as, reading things (issues, PRs, commit history), and — carefully — a write action such as opening a PR or filing an issue.

Heads up: this is a real, shared GitHub repo. Prefer your own branch for anything that writes, and clean up any test issues/PRs you create.

Task 2 — Build a skill (and maybe an agent)

tasks/task-2-skills-agents/
Goal: build at least one skill you'll actually reuse for the rest of the day. A subagent is a good second exercise if you want one.

Skill vs. agent, in one line

A skill is a fixed procedure, invoked by name (or automatically) — same steps every time, like Demo 4's /commit. A subagent is a delegate for open-ended, investigative work — it explores something and reports back without touching your files or your context, like Demo 4's test-runner.

Build a skill you'll use again

Pick at least one — all three get reused in the tasks after this one:

  1. commit-and-push. Extend Demo 4's /commit skill (or build fresh) to also push the branch, and optionally open a PR through the GitHub MCP from Task 1. You'll want this at the end of every task from here on.
  2. THEMA plot style. Apply plot_config.py's theme (set_matplotlib_theme(), get_plot_color()) and drop the colored background on any matplotlib figure, without asking for those steps by hand each time — straight reuse in Task 3.
  3. Branch setup. Creates a uniquely named branch (see the collision note in Getting Started) and switches into the right tasks/task-N-.../ folder in one step.

Optional: try a subagent

Less obvious where these pay off — one candidate that's genuinely useful here:

data-scout — a read-only subagent that explores a new API (Elhub, NVE, ENTSO-E) and reports back what's really there — endpoints, fields, units, gaps — without touching any files. Tasks 4 and 5 both ask you to assess data quality before building; that's where you'd reach for it.

Task 3 — Zero-price hour overlap: NO2 vs. Germany

tasks/task-3-price-notebook/
Goal: a Jupyter notebook plotting, by hour of day, how much NO2's and Germany's zero-price hours overlap in the REF_2030 scenario — then take it from "no style" to on-brand.

Data

THEMA REF_2030 scenario output:

\\jp-s0d9e-001\C on Crunchy 4\00_Model_Analysis\06_Price_Forecast\MAR26\0_Final_Model_Output\Scenario_Output

Files are named like REF_2030_Prices.txt — tab-separated, one row per hour, zone codes (incl. NO2, DEU) as columns, two leading index columns (day-of-year, hour-of-day 1–24), prices in EUR/MWh.

Work through it in four stages, in this order — figuring out how to ask for each stage is the task:

  1. Build it plain. Load both zones' data, compute zero-price hours grouped by hour-of-day, plot the overlap. Plain matplotlib, no custom styling.
  2. Pull in THEMA's actual brand colors. Paste in THEMA's website URL yourself and have the colors sampled from it.
  3. Switch to the repo's plot_config.py instead of hand-picked colors — it already has a "Zero price" color defined, plus zone colors for NO2/DEU.
  4. Remove the colored figure background that plot_config.py's dark theme adds.
Note: the network path is internal — reachable if you're on the company VPN. If you're off VPN and can't reach it, ask Claude to generate a small synthetic REF_2030-style dataset first so you can build the notebook logic, then swap in the real files once connected.

Task 4 — Elhub dashboard: cost of Norgespris to the state

tasks/task-4-elhub-dashboard/
Goal: a dashboard estimating what Norgespris costs the Norwegian state between a chosen start and end date. (Or build a different Elhub-based dashboard entirely — this is just a strong suggestion.)

What is Norgespris?

A voluntary, state-funded fixed electricity price for Norwegian households (not businesses): 50 øre/kWh incl. VAT in most of the country, up to a cap of 5,000 kWh/month for homes (1,000 kWh/month for cabins) — usage above the cap is billed at the ordinary rate. The state settles the difference between that fixed price and the market price. It launched 1 Oct 2025, opt-in via BankID. Ask Claude to verify current details against regjeringen.no's Q&A page before relying on the numbers above — the scheme can change.

Recommended way in

  1. Explain Norgespris to Claude (or point it at the link above) so it has the mechanics right.
  2. Let Claude help you find the data — start with the sources below rather than guessing endpoints.
  3. Assess data quality together: is a figure a real measurement, an estimate, or a proxy? Say so in the dashboard.
  4. Where data is missing, make an explicit, stated assumption rather than silently guessing.

Data sources

WhatWhere
Households on Norgespris, by area elhub.no Norgespris statistics and/or the Elhub API (api.elhub.no/energy-data-api) — check yourself whether the Norgespris counts are queryable there or only on the statistics page; it's unconfirmed either way.

Suggested build order

Number of households on Norgespris → their consumption → the power price → combine into a cost-to-the-state estimate over your chosen date range. Get the first step working and reviewed before adding the next.

Task 5 — NVE hydrological status & year-end simulation

tasks/task-5-hydrology-dashboard/
Goal: a dashboard that takes today's reservoir filling level and simulates where it lands by year-end if the rest of the year follows a historical year's pattern — a first step toward a simple "how critical could this get" tool.

Easiest path: NVE's MCP server

Allemannsdata (a free, no-key community project) runs an MCP server wrapping several NVE datasets — including a get_snow_and_inflow tool: modelled snow and inflow at any point in Norway, from NVE's seNorge grid model (1×1 km, no key) — about as close to "nyttbart tilsig" as you'll get without wrangling raw hydrological data yourself. Connect it:

claude mcp add --transport http nve https://allemannsdata.com/nve/mcp

It also has tools for reservoir fill level/history/min-max-median and hydrological station lookup/observations. Ask Claude what tools the nve server exposes once it's connected, or check the site for the full list.

If you'd rather call the APIs directly

The MCP above wraps NVE's Magasinstatistikk API in part — you can also call it yourself: https://biapi.nve.no/magasinstatistikk/, docs at api.nve.no/doc/magasinstatistikk, no key, JSON, weekly data back to 1995, nationally / per elspot area (NO1–NO5) / per vassdragsområde.

FieldMeaning
fyllingsgradFilling degree, 0–1
fylling_TWh / kapasitet_TWhStored / capacity, in TWh
iso_uke / iso_aarISO week / year
omrType / omrnrArea type (EL = elspot, VASS = watershed, land = national) and number
Correction: "Nyttbart tilsig" (usable inflow) is not a field in this REST API — that's what the MCP's get_snow_and_inflow tool is for. NVE also runs HydAPI (docs: api.nve.no/doc/hydrologiske-data) with raw streamflow ("Vannføring", m³/s) per gauging station — real inflow data, but per station rather than per elspot area, needs a free API key, and needs converting from m³/s to energy units yourself.

Not using the MCP? Derive an inflow-like figure instead

You have weekly storage (fylling_TWh) from Magasinstatistikk. If you also get how much energy was actually produced from reservoirs in the same week, you can back out an approximate inflow from the water balance:

inflow ≈ (storage this week − storage last week) + reservoir production

For reservoir production, use the ENTSO-E Transparency Platform (same free token as Task 4) — "Actual Generation per Production Type", PSR type B12 = Hydro Water Reservoir (distinct from B11 run-of-river and B10 pumped storage), hourly, per bidding zone NO1–NO5. That production figure also directly answers "how much energy was dispatched from the reservoirs" on its own, no derivation needed. This approach ignores spill (water released without generating) — state that as an assumption rather than hiding it.

The simulation

Take this week's actual filling level. For a historical year the user picks, apply that year's week-by-week change in filling degree from the same ISO week forward to year-end, and project where the level lands. Let the user compare several years' paths against the historical min/max/median band for context.

Stretch goal

Use whichever inflow-like series you ended up with to find the years with the worst autumn inflow, and the reservoir fill/production data to find the years where the most water was conserved (smallest autumn drawdown). Let the user cross the two to see the worst-case combination — and show whatever assumptions you made next to the numbers.
